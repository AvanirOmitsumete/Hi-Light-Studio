## Part 1 — User interface

### 1.1 Night theme (default)

Every station now uses a dark, luxurious design based on the Hi-Light Studio logo:

- **Colors:** obsidian-black page, warm charcoal cards, ivory text and metallic gold accents. Borders are thin gold lines; the old heavy black outlines and hard shadows are now soft gold glows.
- **Logo:** the new gold camera logo appears in the top bar. "HI-LIGHT STUDIO" in the top bar and footer uses a gold-foil effect, and a fine gold line separates both bars from the page.
- **Headings:** page titles use **Cinzel**, an engraved capital-letter typeface that matches the spaced "STUDIO" lettering in the logo. The font is stored inside the system, so it works with no internet.
- **Buttons:** black buttons have a gold outline and glow softly on hover. Close (✕) buttons turn gold on hover.
- **Details:** gold text selection, slim gold scrollbars, and a faint gold glow at the top of the page.

### 1.2 Day theme and the Night/Day switch

A **moon/sun switch** sits at the top-right of the top bar on every screen, including the public registration kiosk.

- **Day:** warm ivory page, white cards, champagne-colored header bands and antique-gold accents. Gold text is slightly deeper in Day mode so it stays easy to read on white.
- **Top bar and footer:** stay black in both modes. This frames the page and keeps the gold logo looking right.
- **Per device:** each device remembers its own setting. The kiosk can stay in Night while the cashier laptop uses Day. The choice is applied before the page appears, so there is no flash when a page loads.

### 1.3 What did not change

- **Receipts:** the yellow customer copy and white studio copy look exactly as before, both on screen and on paper.
- **Printing:** always uses the original light colors, whichever theme is on.
- **Signature pad:** stays white with dark ink, in both themes.
- **PDF receipt:** generated separately and unchanged.

### 1.4 Screens checked in a browser

- **Night theme:** Registration, Staff Login, Cashier, Admin and Photographer.
- **Day theme:** Registration and Staff Login.

Not yet viewed: the Cashier, Admin, Makeup, Chooser and Photographer screens in Day mode, the receipt print preview, and every pop-up window. These use the same theme rules as the screens that were checked.

## Part 2 — Workflow fixes

### 2.1 Cancelling a registration keeps its payments

**Before:** "Cancel" in **Admin → Students Directory** deleted the registration permanently, and every payment recorded for it was deleted along with it. Money already collected disappeared from the ledger, leaving unexplained gaps in receipt numbers at end-of-day reconciliation.

**Now:**
- **Cancel** marks the job order **Cancelled**. The record and all its payments stay on file.
- A cancelled order disappears from every station queue: cashier, makeup, photographer and chooser.
- The confirmation message shows how much was already collected and notes that any refund must be handled separately.
- The cancel button is disabled for orders that are already cancelled or released.
- **To restore** a cancelled order: open **Edit Student Record** and change its status back.
- **Server rules:**
  - A job order with **any** payment record can no longer be deleted.
  - No payment can be collected on a cancelled order.
  - A registration with no payments, such as an accidental duplicate, can still be removed.
- **Makeup:** if a makeup artist had already claimed the order, it no longer stays on the artist's screen. Admins still see it so they can release the assignment.

### 2.2 Release only after production is ready

**Before:** the cashier's **Release** button appeared for any paid student, even one not yet photographed. The only check was that the balance was zero.

**Now:** an order can be released only when **all** of these are true:
1. The balance is fully paid (unchanged).
2. Photography is finished.
3. An admin has marked production ready, by setting the main status to **Completed** or **Ready for Pickup**, or the framing status to **Framed** or **Ready**.

What the cashier sees:
- **Green Release button:** the order is ready.
- **Grey Release button:** the order isn't ready yet. Opening it shows a "⏳ Not Ready for Release" panel explaining why, and the confirm button is hidden. If a balance remains, the cashier can still collect it from this window.
- The server enforces the same rule, so an order can't be released early by any route.

**New daily step for the admin:** when prints and frames are finished, mark the order **Ready for Pickup**, either in **Edit Student Record** or in the **Framing Schedule**. Until then, the cashier can't release it.

### 2.3 "Collected Today" shows today's money

**Before:** the **Collected Today** figure on the Cashier screen added up every payment ever recorded, not just today's.

**Now:** it adds up only payments received since **midnight Philippine time** today. Voided and refunded payments are excluded. The figure updates automatically after each payment.

### 2.4 Daily queue number restarts at midnight Philippine time

**Background:** each student has two numbers:
- **Job Order № (e.g. 00042):** the order's permanent ID. It never resets. **This was not affected.**
- **Queue number (e.g. #007):** the student's place in line for that day. It restarts every day.

**Before:** the server used UTC time, which is 8 hours behind the Philippines. The queue therefore restarted at **8:00 AM** instead of midnight. On days with registrations before 8 AM, two students could end up with the same queue number on the same day.

**Now:** the queue restarts at **12:00 midnight Philippine time**, so every queue number is unique within the day.

### 2.5 Pay Now failed on network stations

**Before:** on any station that opens the system at the server's network address (for example `http://192.168.1.50:8090`), **Confirm & Print Receipt** failed with *"Payment processing failed: crypto.randomUUID is not a function"*. No payment was recorded.

**Cause:** the cashier screen created each receipt's internal reference with a browser feature that only works on secure (HTTPS) pages or on the server PC itself (`localhost`). The studio network uses plain HTTP, so the feature was missing on every other device.

**Now:** receipt references are created a different way that works on every station. They are still random and unique, so the protection against recording the same payment twice is unchanged.

**Related fix:** the photographer's **Copy Path** button had the same limitation. It now falls back to a copy method that works on plain-HTTP stations.

### 2.6 New: camera auto-import

**Before:** the photographer copied each client's photos into their folder by hand, using **Copy Path**.

**Now:** the system watches the camera's output folder and moves each new photo into the folder of the client being shot.

**Setting it up (once per camera):**
1. Open **Admin → Camera Import**, or press **Set Up** on the Photo Floor.
2. Enter a name (e.g. *Booth 1 — Canon R6*) and choose the camera's output folder on the server PC with **Browse**. A new folder can be created from the same window.
3. Options: **Camera is on**, **Look inside subfolders** (for software that saves into dated folders) and **Also import RAW files** (saved to the client's `RAW` folder; the chooser only shows JPEG/PNG).
4. In the camera's tethering or transfer software (EOS Utility, Lightroom, Capture One, Wi-Fi/FTP…), set the same folder as the save folder. If the camera is tethered to a different PC, share the folder on the network and save to the share.

**Using it on the Photo Floor:**
- Choose the camera under **Camera Auto-Import → This device**. Each device remembers its choice.
- **Call Client** links the camera to that client. The panel shows "Sending photos to …" with a live photo count; the client's card shows "sending photos here". **Link Camera** on the card does the same for a client already on set.
- New shots reach the client's folder within about 4 seconds. A photo still being written is never moved; it is picked up once the camera software finishes it.
- **Mark Done** sends the last shots and unlinks the camera. **Stop Sending** unlinks without finishing the shoot.
- Photos that were already in the folder when a client was linked, or taken with no client linked, are **not** assigned automatically. The panel shows how many are waiting, with a button to send them to the current client.
- A repeated file name gets a suffix (`IMG_0001_2.jpg`); nothing is ever overwritten.

**Rules:** the camera folder must be separate from the client photo folders and can't be a whole drive or a system folder; two cameras can't share a folder. Photographers and admins can add and edit cameras; only admins can remove them.

Step-by-step setup, including LAN folder sharing: [Camera Auto-Import guide](../CAMERA_AUTO_IMPORT_GUIDE.md).

### 2.7 New: job order sheet, payment receipts and cash change

**Before:**
- The job order printed on two full pages.
- It had no receipt number, payment date, payment method or list of payments.
- The cashier screen had no "cash received" field, so change was always saved as ₱0.
- The kiosk printed an "UNPAID" stub before the client had paid.

**Now:**

| Form | Paper | When it prints | Copies |
|---|---|---|---|
| **Job order** | 1 letter sheet, cut crosswise | After the client's **first** payment (downpayment or full) | Top half: **customer claim stub** with the full terms. Bottom half: **studio accounting copy** with a one-line terms note and a "Claimed by / Date" line |
| **Payment receipt** | Top third of a letter sheet (3.67 in tall; the rest stays blank for later receipts), cut lengthwise | After **every later** payment (additional payment or final settlement) | Left: **customer copy**. Right: **studio copy** with a customer signature line |

- **Both halves of the job order show:**
  - client, school and package details;
  - a **payment table** (date, receipt no., payment type, method, amount, balance after; the studio copy also shows cashier and reference);
  - total, amount paid, balance and a FULLY PAID / WITH BALANCE mark.
- **The payment receipt shows:**
  - receipt no., date and time, job order no. and client;
  - payment type, method and reference;
  - previous balance, **amount paid**, cash received, change and remaining balance;
  - FULLY SETTLED once the balance reaches zero.
- **Official receipt numbers:**
  - The server assigns them in order (**OR-000001**, **OR-000002**, …), one per payment.
  - Payments made before this update keep their old reference numbers.
- **Cash received:**
  - For cash payments the cashier enters the cash handed over, or presses **Exact**. Change is shown on screen as it's typed.
  - The server works out the change again and saves it.
  - Payment can't be confirmed if the cash is less than the amount.
- **Saved payments are locked:**
  - Receipt number, amount, method, cash, change and balances can't be edited afterwards.
  - Admins can still void or refund a payment, or add a remark.
  - A voided payment prints with a **VOIDED** stamp and is crossed out in the payment table.
- **Reprinting:**
  - From the cashier list, **Print** opens the job order. Switch to **Payment Receipt** and pick any payment to reprint its receipt.
  - In Admin → Analytics, **Reprint** on a payment row opens that payment's form.
- **PDF:**
  - The **PDF** button downloads the same layout (job order sheet or receipt strip).
  - In Admin → Students, **PDF** downloads the job order sheet.
- **Kiosk:**
  - After registering, the kiosk shows only the job order and queue numbers.
  - The client gets the printed claim stub from the cashier after paying.
- **Fitting on half a sheet:** the payment table fits 4 rows. With more payments, voided ones are left off first, then the oldest, and the stub notes how many are on file.

**Saving paper and ink:**
- **Receipts use the same letter bond paper.** A receipt prints on the top third only (3.67 in), so one sheet holds 3 receipts. Cut along the dashed line and keep the rest of the sheet.
- **Leftover pieces get used.** For a later receipt, choose **Paper: Leftover piece** in the print window, load the piece, and pick Paper size **Statement (5.5 × 8.5 in), landscape**. The receipt prints at the top of the piece. Each station remembers its paper choice.
- **No solid fills.** The forms use outlines and plain text only: no solid black or gold blocks or header bars.

### 2.8 New: walk-in clients and the school / walk-in switches

**Before:** every client had to pick a school, level and course, so the system only worked for graduation pictorials.

**Now:** the studio can take two types of clients.

| | School / Graduation | Walk-in |
|---|---|---|
| Who | Students through their school | Family and personal portraits; events outside the studio (weddings, birthdays, company events) |
| Kiosk asks for | School, level, course, section, student ID | Type of session, organization/company (optional), notes; **event date and venue** for events outside the studio |
| Packages shown | Packages set to *School* or *Both* | Packages set to *Walk-in* or *Both* |
| Terms | Graduation terms (unchanged) | Walk-in terms, editable in Admin |
| Photo folder | `SCHOOL\COURSE\00012_Name_…` | `WALK-IN\2026-12\00012_Name_…` |
| Printed job order | School / Department / **Course acronym** · Section | Session / Organization / Event date / Venue |

**Admin → Client Types & Sessions:**
- **Two switches:** *School / Graduation* and *Walk-in Clients*.
  - Walk-ins start **OFF**, so for a graduation event the kiosk shows the school form only.
  - When a walk-in arrives, the admin switches walk-ins **ON**. The kiosk then asks the client which type they are.
  - At least one switch must stay on.
- **Session types:** add, edit or switch off session types. "Outside the studio" makes the kiosk ask for the event date and venue.
  - Starting list: Family Portrait, Solo / Personal Portrait, ID / Passport Photo, Pre-Wedding / Prenup, Wedding, Birthday / Debut, Corporate / Company Event.
  - A session type already used by a job order can only be switched off, not deleted.
- **Walk-in terms:** edit one clause per line. They are shown at the kiosk and printed on walk-in claim stubs. **Please review the starting text with the studio owner.**

**Elsewhere:**
- **Packages & Add-ons:** each package has *Offered To: School / Walk-in / Both*. Existing packages are set to School.
- **Cashier, Photo Floor, makeup, chooser and Admin lists:** show "Walk-in · Wedding" (or the client's company) where they show the school and course.
- **Clients Directory** (was Students Directory): has a *Walk-in clients* filter. Its edit window shows session, organization, event date and venue for walk-ins.
- **Overall Excel export:** has a **WALK-IN OVERALL** sheet when there are walk-in clients.
- **Printed job orders and receipts** show the **course acronym** (e.g. BSCS) instead of the full course name.

**Not changed:** add-ons are shared by both client types. The school roster lookup is shown only on the school form.

## Part 4 — Putting the update live

1. On the studio server PC, run **`run.bat --build`**. This rebuilds the app and serves it on port 8090. Until this is done, stations keep showing the previous version.
2. On each station, refresh the browser.
3. The camera import adds one new table (`camera_stations`). PocketBase creates it automatically on start; existing orders keep their data.
4. Set up each camera in **Admin → Camera Import** (see 2.6).
5. The receipt update adds three fields to payments and fills in the balances on past payments automatically. Only **letter** bond paper is needed. Keep the rest of each sheet for later receipts (see 2.7).
6. The walk-in update adds the studio settings and session types, and marks every existing job order and package as *School*. **Walk-ins start switched OFF**; switch them on in Admin → Client Types & Sessions when needed.

**After going live:**
- Orders that are already shot and finished must be marked **Ready for Pickup** (or Completed / Framed / Ready) before the cashier can release them.
- Today's queue numbers continue as normal. The midnight reset applies from the next new day.

## Part 5 — Known limitations and suggested next steps

These were noted during the workflow review and were **not** changed in this update:

- **No refund or void screen.** Payments can be voided or refunded only through the database admin panel (`/_/`). A cancelled order that was paid still counts as collected until its payment is marked refunded. A refund button in Admin would close this gap.
- **Downpayment is fixed at exactly 50%.** Many studios accept any downpayment amount.
- **Production status is set by hand.** Moving an order to Completed or Ready for Pickup is done manually in Admin; it isn't linked to the chooser's photo confirmation.
- **No retake or no-show step** in the photographer's queue.
- **Soft-copy delivery** (Google Drive or USB) isn't tracked as a step; it appears only in the receipt terms.
